## Lens: arch-skeptic

### Recommended path
C

### Why this path under the arch-skeptic lens

Path C (GitHub App with `contents: read` scoped to the SCP repo) is the only option in the shortlist that removes the failure without creating an architecturally worse substitution failure. The observed failure at lines 107 and 1149 of `policy-check.yml` is specifically that the **default `GITHUB_TOKEN` from an adopter context carries no read grant on a private third-party repo**. Path C removes that exact deficiency by introducing an installation token whose scope is deliberately bounded: `repository_permissions: { contents: read }` on `jrnb2024/standards-control-plane-` only. The App token is obtained inside SCP-controlled workflow code and is never surfaced to the adopter — `secrets: inherit` is still explicitly prohibited per ADOPT-001 §12.7.10 and the federation primitive's invariant 2 (§4 of the plan-doc) is fully preserved. That invariant is the **trust-root** of the entire cascade: it is what makes WP-SCP-024's canary-first sequencing safe to run against production branches, because adopter-side named secrets can never silently leak into SCP workflow code regardless of what any future SCP version declares.

The federation primitive's existing evolution path — v1.0.0 → v1.1.0 → v1.2.0 → v1.3.0, each cut as a tag-protected SHA on `main`, propagated via Renovate to adopters — is entirely undisturbed under Path C. No adopter wrapper changes. No change to the checkout mechanism as seen by Renovate. The SHA pin still resolves to a specific commit inside the private repo; the only difference is that when the reusable workflow executes the cross-repo `actions/checkout` steps at lines 107 and 1149, it exchanges the App's installation key for an ephemeral token rather than falling back to the caller's `GITHUB_TOKEN`. The Renovate preset, tag-protection ruleset (D-030, D-034), and the `version-manifest.json`-based freshness check in `policy-check.yml` (ADOPT-001 §12.7.11) all stay structurally identical.

Path C is also the **only path on the shortlist whose failure mode upon misconfiguration is recoverable and diagnosable** with the existing error-code infrastructure. If the App is misconfigured or its installation is revoked for a specific adopter, the cross-repo `actions/checkout` fails with an authentication error; that maps to `SCP-E001` (infra fetch fail), the same error code the workflow already emits for binary-download failures. The adopter sees a clear, named signal. Under Path A, misconfiguration does not exist — but if SCP later needs to restrict visibility, there is no error-code path: the damage is already done. Under Path D, if the bundle-build pipeline fails to publish for a given tag, the workflow gets a 404 on the release asset download — a new, structurally different failure surface that the existing SCP-E001 taxonomy was not designed to distinguish from other infra failures.

### Failure-surface analysis — does this path's NEW failure surface exceed the failure it removes?

**Path A.** The new failure surface is strategic rather than operational. Making the repo public does not introduce a runtime failure surface — in fact it removes one (the auth failure). But it introduces a **permanent exposure surface** with no rollback: SCP's full operational history (dispatch notes, operator decisions, R-cycle evidence trails, DECISIONS.md rows, plan-docs including this one) becomes public. WP-SCP-020 §8 and WP-SCP-024 §2 both acknowledge bus-factor-1 single-operator mode; the `docs/reviews/` tree contains a high-fidelity map of exactly how the estate trust chain works. An adversary with that map can construct a precise supply-chain attack (e.g., knowing the tag-protection ruleset ID 15752458 from WP-SCP-020 §3). The compensating consideration in the plan-doc (ADRs are already public-describable) does not hold fully — ADRs describe *what* was decided; `docs/reviews/` evidence trails describe *why* defences are shaped the way they are, which is the more actionable intelligence for an attacker. The failure this path removes is one GitHub Actions runner-scope deficiency per PR; the failure it introduces is permanent strategic exposure on the entire estate's trust architecture. That substitution is worse.

**Path C.** The new failure surface is the App's private key custody under D-031 single-operator mode. If the private key is compromised, an attacker can obtain an installation token and clone the SCP repo. This is narrower than Path A's exposure because: (a) the attacker would need to compromise the SCP repo's secrets storage (not just have network access to a public URL), and (b) the scope is bounded to `contents: read` on one repo — no write surface, no adopter-secret exfiltration. The App-install ceremony per adopter is real friction, but it is a one-time onboarding cost per adopter, not a recurring operational burden. The new failure surface (key compromise) is **smaller than the failure it removes** (permanent public exposure of the full estate trust map). This is the correct side of the trade-off.

**Path D.** The new failure surface is the bundle-build pipeline itself. Per the plan-doc §5: "Bundle build pipeline becomes a new failure surface — bundle authoring + publishing slice required at every release." This is structurally load-bearing in a way that Path C's App-key custody is not: key custody is an access-management problem with established mitigations (rotation, scoped secrets, audit trail); a bundle-build pipeline failure blocks every adopter from receiving SCP updates until the pipeline is fixed and a new release is cut. Under Path D, a failure during an SCP point release would stall the entire Renovate cascade across all 5 WP-SCP-024 cohort adopters simultaneously. WP-SCP-024 invariant 8 (bake must observe a live Renovate bump cycle) could not be satisfied until the pipeline is repaired and a new tag is cut. The failure surface introduced by Path D is **correlated across the entire cascade** — a property the current checkout-based distribution explicitly avoids, because each adopter's SHA pin resolves independently of any build artefact pipeline.

### Reversibility ranking

Cheapest to most expensive:

1. **Path C.** Reversal mechanism: delete the GitHub App (or revoke per-adopter installations). Revert the "obtain App installation token" step added at the top of the cross-repo checkout steps in `policy-check.yml`. The reusable workflow reverts to the same failure mode as today (caller `GITHUB_TOKEN` insufficient). No adopter wrapper changes. Cost: one PR on the SCP repo + operator-attended App deletion. Timeline: <1 day. This is a clean architectural un-do because the App is an external credential, not a structural change to the distribution mechanism.

2. **Path D.** Reversal mechanism: revert `policy-check.yml` from bundle-download to checkout-based distribution; remove the bundle-build step from the SCP release pipeline; bump Renovate configuration back to SHA-pinned checkout shape. All adopter wrappers must re-pin to a checkout-mode SHA (Renovate handles this, but it requires a version cut and a Renovate cycle per adopter — 5 adopters × 1 Renovate cycle each). Cost: multi-PR SCP-side rewrite + coordinated Renovate cycle across all onboarded adopters. Timeline: 1–3 weeks. The reversal is possible but requires a synchronised release cut and a cascade-wide Renovate sweep.

3. **Path A.** Reversal mechanism: none for historical content. A private-again flip stops new public access but does not remove what has already been cloned, cached, or indexed. The strategic information exposed (operational history, trust-chain architecture, CODEOWNERS patterns, ruleset IDs) is irrecoverable. Cost: operationally trivial to flip visibility back; strategically permanent. Timeline for partial recovery: indefinite. This is architecturally irreversible in the sense that matters — the decision commits every future operator of this estate to treating the SCP operational history as permanently public, forever.

### Pareto-frontier coverage check

Neither Path E nor Path F is strictly Pareto-better than Path C under the arch-skeptic lens.

**Path E (public mirror).** Path E preserves §12.7.10 and keeps the SCP source private, but it introduces a **mirror-lag failure surface** that Path C does not have. If the sync pipeline fails, adopters get a stale federation primitive with no signal — the checkout succeeds but the content is from a prior tag. Under Path C, a misconfiguration is loud (SCP-E001). Mirror-lag is silent. More importantly, Path E requires adopter wrappers to change their `uses:` reference from `jrnb2024/standards-control-plane-` to `jrnb2024/standards-control-plane-mirror` — a cascade-wide wrapper update across all 5 cohort adopters plus any future adopters. That is a higher adopter-onboarding cost than Path C's App-install ceremony. Path E is therefore **dominated by Path C** on the silent-vs-loud failure axis and on adopter-side migration cost. It is escalation-eligible per §10 STEP 1 if A/C/D all fail, but it is not Pareto-better than C.

**Path F (hybrid private source + public artefact).** Path F combines Path D's bundle-build pipeline with a companion public repo for artefact hosting. This inherits all of Path D's bundle-build failure surface plus adds the companion-repo coordination surface (mirror lag, companion-repo access management). It is not Pareto-better than Path C on any arch-skeptic axis. Escalation-eligible per §10 STEP 1, not a winner.

**Escalation recommendation.** Neither E nor F constitutes a §10 STEP 1 escalation candidate from this lens. The A/C/D shortlist is sufficient; Path C clears the acceptance bar. No escalation is warranted.

### Operational-debt comparison

**Path A.**
- Permanent strategic-information-management debt: every operational decision, R-cycle evidence trail, and plan-doc in the SCP repo is now permanently public. Any future internally-sensitive artefact must be excluded from this repo by default (requires a `standards-control-plane-private` companion repo and split authoring discipline — new cognitive overhead for every future operator).
- No credential-rotation debt (no new credentials).
- No release-pipeline debt.
- Ongoing review-redaction debt: DISPATCH-NOTEs, DECISIONS.md rows, and STATUS.md entries would need to be authored with the assumption of public readership, changing the cognitive overhead of every future governance event.

**Path C.**
- App private-key rotation debt: the App's private key must be rotated on a schedule (recommended: 90-day rotation per GitHub App security guidance). Under D-031 single-operator mode, this is a single-operator ceremony with no delegation. If @jrnb2024 is unavailable during a rotation window, the installation tokens continue to work until the key expires (GitHub App keys have configurable TTL) — not a hard outage, but a trailing credential risk.
- App-install ceremony per adopter: one-time for each of the 5 WP-SCP-024 cohort adopters. Requires org-admin access on the adopter side. For single-operator estates (PIM, mapp-doc-agent, etc., all under @jrnb2024), this is a single-operator action; for external adopters who join later, this becomes a documented onboarding step in ADOPT-001 §12.7.
- ADOPT-001 §12.7 update debt: a new sub-section (§12.7.N) must document the App-install ceremony, token-scope, and what to do if the installation is revoked. Estimated: one ADOPT-001 amendment PR, medium-complexity.
- OIDC-vs-App-key complexity: the plan-doc (§5, Path C description) describes "OIDC + App pattern" as the mechanism. This is more complex than a PAT pattern and requires careful documentation of the token-exchange step in `policy-check.yml`. The step is verifiable (the App token scope is auditable via the GitHub API) but adds a new code surface in the workflow that must be maintained across version bumps.

**Path D.**
- Bundle-build pipeline debt: a new CI job must run on every `v*` tag cut, building the policy bundle, packaging it as a GitHub Release asset, and publishing it with hash-attestation (cosign/Sigstore) per the plan-doc's risk surface note. This is a new operator ceremony per release cut — estimated 30–60 minutes of operator attention per minor version (currently v1.0.0 → v1.1.0 → v1.2.0 → v1.3.0 = 4 releases in 5 weeks). Under D-031 single-operator mode, every release is blocked until the bundle build succeeds and is verified.
- Bundle-version-to-SHA-pin mapping debt: adopter wrappers today pin to a commit SHA; bundle downloads pin to a release version. These are different trust anchors. Renovate must be reconfigured to track release versions instead of (or alongside) commit SHAs. The SCP Renovate preset (020F, `renovate/v*` tag series) would need a new regex-manager block. This is an ongoing maintenance surface: every future Renovate preset version bump must also cover the bundle-version tracking.
- Sigstore/cosign attestation debt: the plan-doc's risk surface for Path D explicitly requires hash-attestation on bundle artefacts. OPA and Conftest do not currently publish Sigstore attestations (ADOPT-001 §12.7.13, TF-007). Adding bundle-level attestation introduces a new Sigstore verification step that must be maintained in parallel with the existing binary-level SHA256 checks — not a blocker, but a non-trivial new supply-chain surface.

### Risk surface accepted under this recommendation

1. **App private-key single-point-of-failure under D-031 single-operator mode.** The App's private key is held in SCP repo secrets. Key compromise allows an attacker to obtain `contents: read` installation tokens on the SCP repo. Mitigation: key is not user-scoped (unlike a PAT), scope is bounded to one repo, rotation schedule can be enforced via GitHub App credential management. Accepted as smaller than Path A's permanent strategic-information exposure.

2. **App-install ceremony creates a new per-adopter onboarding friction point.** Each adopter's org-admin must approve the App installation. For the current 5-cohort (all under @jrnb2024 in single-operator mode), this is a self-install and is operationally trivial. For future multi-org adopters, this introduces a coordination step. ADOPT-001 §12.7 must be updated with the install procedure; any adopter whose org-admin is slow to install blocks that adopter's TF-PIM-001 resolution.

3. **OIDC + App token-exchange adds a new workflow step that is not covered by existing selftest fixtures.** The `workflow-selftest` harness (020B.1) tests the reusable workflow against fixture-pass and fixture-fail paths. The new token-exchange step is in the workflow preamble, before fixture-based evaluation. A selftest path must cover the token-exchange failure case (App key misconfigured or installation missing) to prevent regressions on future workflow versions.

4. **D-031 quarterly review at 2026-07-21 is the natural escalation point for App-key custody.** If a second maintainer joins before that review, they should be granted co-custody of the App private key to eliminate the single-operator key-custody risk. This is not a blocker on the recommendation but is a load-bearing tracked-forward item.

### Decision points (from plan-doc §6) resolved by this recommendation

- **Decision point 2 (Distribution-mechanism choice).** RESOLVED: retain checkout-of-source (Path C). The cross-repo `actions/checkout` steps remain structurally unchanged; only the token source is updated. No pivot to release-artefact distribution.
- **Decision point 3 (Reversibility tolerance).** RESOLVED: the estate tolerates workflow-level reversibility cost (Path C is reversible at workflow-level) but not strategic-irreversibility cost (ruling out Path A) and not distribution-mechanism-pivot cost (ruling out Path D).
- **Decision point 4 (PAT/App custody disposition).** RESOLVED: App credential, not PAT. The App's private key is SCP-repo-secret-held; adoption of the App does not require adopter-side PAT management. Rotation is App-credential rotation under SCP's control, not per-adopter PAT rotation.
- **Decision point 5 (Adopter-onboarding cost vs SCP-side cost).** RESOLVED: modest adopter-side cost (one-time App install per adopter) accepted in exchange for preserving the invariant set and avoiding SCP-side strategic exposure (Path A) or SCP-side pipeline complexity (Path D). For the current 5-cohort under single-operator mode, the adopter-side cost is effectively zero (self-install).
- **Decision point 6 (Sequencing relative to v1.3.0).** Path C's implementation is a single slice: one PR adding the token-exchange step to `policy-check.yml` + the App registration + ADOPT-001 §12.7 update. This is compatible with v1.3.0 sequencing. The plan-doc §8 order-of-operations for Path C is: ADR → implementation slice → SCP selftest green → external-adopter cross-repo verification → PIM required-check restoration. All steps are within a single release cycle. v1.3.0 ships SCP-R-005 AND the working external-adopter path simultaneously.
