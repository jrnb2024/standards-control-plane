## Lens: sec

### Recommended path
C

### Why this path under the sec lens

The trust-model question at the core of TF-PIM-001 is not "which path is cheapest" but "which path preserves the tightest principal boundary between SCP-controlled code and adopter-repo secrets while solving the cross-repo checkout problem." Under that framing, Path C (GitHub App with `contents: read` scoped only to the SCP repo, token obtained by SCP-controlled workflow code, never surfaced to the caller) is the only path that solves the authentication problem *while simultaneously doing no damage to the threat-model boundary that exists today*.

Path A (make SCP repo public) solves the checkout problem by eliminating the need for authentication entirely, which is technically clean at the workflow layer — invariant 2 is fully preserved and §12.7.10 is never touched. But the threat-model exposure is real and irreversible. The plan-doc §5 (Path A "Risk surface") identifies four categories: policy logic exposure, vendoring/lock-file patterns, issue/PR history including DISPATCH-NOTEs and R-cycle governance evidence, and foreclosed future private-artefact staging in the same repo. Of these, the first is the least worrying (as the plan-doc notes, ADRs already document the rationale for each rule publicly). The second is more material: `scripts/scp-policy-check.lock` — the SHA256-pinned supply-chain root-of-trust per ADOPT-001 §12.7.13 — becomes visible to any actor scoping an attack on the SCP supply chain. An adversary can pre-compute what binary substitution would pass SHA256 verification on a lockfile they can now read. This is not a catastrophic exposure under today's download-and-verify-at-runtime model, but it shrinks the defensive depth. The third category — DISPATCH-NOTEs, R-cycle evidence, governance content — is the exposure the sec lens weights most heavily as operationally irreversible: once the PR history is public, operator strategic signals about adoption decisions and security-finding remediation rationale are permanently indexed. Path A is therefore "clean at the layer it touches, leaky at the layers it doesn't." Path A's irreversibility means if the operator changes threat model (adds proprietary domain rules, begins staging private-only content) the only remedy is a second repo with a split workflow, which is the architecture Path E offers — but Path E was dropped from the shortlist.

Path D (public Release artefacts) solves the checkout problem by pivoting the distribution mechanism: the workflow downloads a bundle from GitHub Releases instead of performing a `git clone`. The auth-surface at the workflow layer is clean — no token, no `secrets: inherit`, invariant 2 preserved. The sec problem with Path D is not its auth surface but its attestation surface. As noted in ADOPT-001 §12.7.13, even the current `gh attestation verify` for OPA runs against a 404 (OPA v1.x has not published Sigstore attestations to GitHub's attestation database — tracked as TF-007). Path D requires building a *new* attestation layer on top of release artefacts to achieve trust-rooting parity with the current checkout-at-tag-SHA pattern. The current trust root is: D-030 tag-protection on `v*` (no force-push, no deletion) + required-signed-commits on `main` (D-030) + CODEOWNERS on `scripts/**` protecting the lockfile + `gh attestation verify --signer-workflow` on scorecard emits (D-042). A release bundle substitutes a new unit — the `.tar.gz` — for the git-tree-at-SHA unit. To root trust in the bundle at the same level, it needs a Sigstore / cosign attestation pinned to the same tag-protected SHA. Given that TF-007 is already open because OPA upstream doesn't yet publish Sigstore attestations, the plan-doc's statement that "release-artefact publishing must be hash-attestation-verified (cosign / Sigstore) to maintain trust-rooting parity" (§5, Path D "Risk surface") describes work that the SCP team would have to build and maintain itself. The `gh attestation verify --signer-workflow` pattern used in D-042 (scorecard aggregator) is the closest existing analogue — it verifies the GitHub Actions workflow that signed an artefact, which is exactly what a bundle-attestation would need. But scorecard emits are produced inside the reusable workflow (so the signer-workflow is the federation primitive itself), whereas a release-bundle attestation would be produced by a new release-build pipeline job. That new pipeline is a new failure surface and a new trust-claim to maintain. Until TF-007 closes upstream, Path D's attestation parity is achievable only by SCP-side cosign, which introduces an SCP-held signing key — the same custody problem Path C has for the App private key, but with fewer off-the-shelf rotation mechanisms.

Path C avoids both of these problems. The GitHub App private key is a custody problem, but it is a well-understood one with clear operational analogues in the estate (CT-016's service-account + API-key admin surface per ADOPT-001 §11.5 is an operational-doc-pending parallel). The App's scope is bounded: `repository_permissions: { contents: read }` on `jrnb2024/standards-control-plane` only. Even if the App private key leaks, the attacker gains read access to the SCP repo's contents — functionally equivalent to Path A's permanent public exposure, but *recoverable*: rotate the key, revoke the installation, re-issue. Path A's exposure is permanent. Path C's is a recoverable incident. Under D-031 single-operator-mode, key custody is a bus-factor-1 problem (the same risk the plan-doc acknowledges for every SCP-side governance artefact), and the mitigation shape is identical to the quarterly review cadence already accepted for D-031: the 2026-07-21 quarterly review should add App-key rotation verification to its agenda.

### Federation-primitive invariants 1-5 disposition under this recommendation

**Invariant 1 — Adopter token does not leave adopter context.** Preserved. Path C does not change the token-handling logic for the caller's `GITHUB_TOKEN`. The App installation token is obtained by SCP-controlled workflow code using the App private key stored in SCP's secrets — it is an SCP-side credential, not a caller credential. `persist-credentials: false` on every `actions/checkout` step (lines 95, 113, 1154 of `policy-check.yml`) is unchanged. The adopter's `GITHUB_TOKEN` is still never written to artefacts or forwarded to network calls beyond the runner.

**Invariant 2 — SCP-controlled workflow code never sees adopter named secrets.** Preserved. This is Path C's primary claim over Path B. No `secrets:` declared on the reusable workflow; adopter wrappers never add `secrets: inherit`. The App token is generated inside the reusable workflow using a credential SCP already holds (the App private key stored as an SCP-repo secret, not passed in from the caller). The forward-compatibility caveat in ADOPT-001 §12.7.10 — "a future SCP version that introduces any named `secrets:` declaration would retroactively pass every caller secret to the workflow on adopter repos that pre-emptively added `secrets: inherit`" — never materialises under Path C.

**Invariant 3 — Trust roots in tag-protected SHA pins.** Preserved, with one nuance. Adopter wrappers continue to pin to `policy-check.yml@<SHA>` at a tag-protected release (D-030 + D-034). The App-token-generation step added to the workflow in Path C is itself covered by the same SHA pin — adopters can audit exactly which `generate-app-token` action version and which token-generation logic they are consuming. The App's own GitHub-side configuration (scopes, installations) is not SHA-pinned, but the *code that consumes the App token* is. This is a partial relaxation — the App's permission scope at GitHub is an out-of-band trust element — compensated by the limited scope (`contents: read` on one repo only) and by the App installation being adopter-side visible (each adopter's GitHub org admin can audit their App installations).

**Invariant 4 — Policy bundle integrity is verifiable.** Preserved. The `scripts/scp-policy-check.lock` SHA256 verification of OPA, Conftest, and Regal binaries (ADOPT-001 §12.7.13) is unaffected by the auth-mechanism change. The checkout still lands the same tree; bundle integrity verification runs against the same content. The Sigstore soft-warn status (TF-007) is unchanged.

**Invariant 5 — Annotation surface is fixed.** Preserved. SCP-EXXX error codes are a closed set (ADOPT-001 §12.7.7). Path C introduces no new annotation surface; the App-token step is an internal workflow implementation detail, not a new annotation-emitting step visible to adopters.

### Risk surface accepted under this recommendation

1. **App private key custody is single-operator under D-031.** The App private key stored as an SCP-repo secret is held by @jrnb2024 exclusively. Loss or compromise of the key grants `contents: read` on the SCP repo (recoverable via key rotation + App deletion) but a key-rotation failure or account compromise blocks every external adopter simultaneously. Mitigation: the 2026-07-21 quarterly D-031 bus-factor-1 review must be extended to cover App-key rotation verification, and a documented rotation SOP must be part of the impl WP plan-doc.

2. **App installation revocation is a per-adopter ceremony.** If an adopter needs to exit the federation primitive, de-adoption today is a wrapper-deletion + branch-protection-removal ceremony (ADOPT-001 §12.7.5). Under Path C, it also requires App-installation revocation from the adopter's GitHub org/account settings. This is an additional off-boarding step not covered in ADOPT-001 §12.7.5 today; without updating that section, de-adoption would leave a residual App installation with `contents: read` on the SCP repo. The blast radius of a residual installation is read-only access to the SCP repo from the adopter's runner context — but under Path A this would be permanent public read anyway. Still requires ADOPT-001 §12.7.5 update.

3. **App installation ceremony requires adopter-side org-admin access.** The plan-doc §5 (Path C "Risk surface") correctly identifies this as onboarding friction. Under D-031 single-operator-mode on the SCP side, @jrnb2024 cannot perform the App installation on behalf of adopters — each adopter must have someone with org-admin permissions perform the install. For the 5-adopter cohort (PIM, control-tower, mapp-doc-agent, recommender, shopify-app), all are personal/small-org repos where @jrnb2024 may have sufficient access; this requires confirming the install-path per adopter before the impl slice opens.

4. **The `generate-app-token` action step is a new third-party action dependency.** Whichever action generates the App installation token (e.g., `tibdex/github-app-token`, `actions/create-github-app-token`) must be SHA-pinned and CODEOWNERS-protected like every other `uses:` in `policy-check.yml`. This is a new supply-chain dependency. The impl WP plan-doc must name the exact action, pin it, and add it to the lockfile attestation tracking.

5. **App token is short-lived but the installation is long-lived.** GitHub App installation tokens expire after 1 hour — this is appropriate for a CI job. The long-lived risk is the installation itself, which persists until an adopter explicitly revokes it. An adopter whose repo is compromised (a malicious PR that exfiltrates runner-context secrets) gains a short-lived token with `contents: read` on the SCP repo during the job run. This is bounded to the runner's lifetime and is no worse than Path A's permanent public exposure.

### Decision points (from plan-doc §6) resolved by this recommendation

- **Decision point 2 (Distribution-mechanism choice — checkout-of-source vs release-artefact-download).** Resolved: Path C retains checkout-of-source. The three `actions/checkout` sites in `policy-check.yml` (lines 92, 107, 1149–1154) are unchanged in mechanism; only the token source on the two SCP-repo checkout steps changes to use the App installation token.
- **Decision point 3 (Reversibility tolerance).** Resolved: Path C is reversible at workflow-level cost. App deletion or App-installation revocation restores the pre-TF-PIM-001 failure mode (cross-repo checkout fails, adopter blocked). This is preferable to Path A's effective irreversibility. The sec lens's weighting is: bounded-recoverable exposure over unbounded-permanent exposure.
- **Decision point 4 (PAT/App custody disposition).** Partially resolved by the sec lens: App-credential custody is an acceptable D-031-symmetric risk provided the 2026-07-21 quarterly review explicitly covers App-key rotation (see tracked-forward items below). The impl WP plan-doc must specify the rotation SOP and the account-compromise response procedure.
- **Decision point 5 (Adopter-onboarding cost vs SCP-side cost).** Not resolved definitively — belongs primarily to the pragmatist lens. The sec lens notes only that the org-admin-access requirement (risk item 3 above) must be verified per adopter before the impl slice opens; if any cohort adopter cannot perform the install, Path C's cost model changes materially.
- **Decision point 6 (Sequencing relative to v1.3.0).** Not resolved by the sec lens; belongs to pragmatist.

### Tracked-forward items this recommendation generates

- **TF-PIM-001-SEC-001 — App-credential rotation SOP.** The impl WP plan-doc must specify: (a) how the App private key is generated (GitHub App settings → "Generate a private key"); (b) how it is stored as an SCP-repo secret (repo-level, not org-level, scoped to the Actions context only); (c) the rotation trigger conditions (calendar: annually minimum; event: suspected compromise, account access change, D-031 quarterly review); (d) the rotation procedure (generate new key → update repo secret → verify at least one adopter runs successfully → delete old key); (e) the account-compromise response (delete App entirely → rotate key has no meaning if GitHub account is compromised; App deletion revokes all installation tokens within minutes).

- **TF-PIM-001-SEC-002 — ADOPT-001 §12.7.5 de-adoption update.** The de-adoption procedure must be extended to include App-installation revocation as a required step: "after deleting the wrapper and removing the required-check, the adopter's GitHub org-admin must revoke the `scp-federation-primitive` App installation from Settings → Integrations → GitHub Apps. A residual App installation with `contents: read` on the SCP repo represents a persistent unnecessary access vector and does not expire automatically."

- **TF-PIM-001-SEC-003 — `generate-app-token` action SHA-pin and supply-chain registration.** The impl WP plan-doc must name the exact action used to generate the App installation token, provide its 40-character commit SHA pin, confirm it is added to the workflow's `uses:` pinned-SHA set, and confirm CODEOWNERS coverage on `.github/**` extends to it. The action must be evaluated for Sigstore attestation status (same TF-007 parallel) before the impl slice opens.

- **TF-PIM-001-SEC-004 — Per-adopter App-install access verification.** Before the impl slice opens a PR, verify that each of the 5 cohort adopters (PIM, control-tower, mapp-doc-agent, recommender, shopify-app) has an org-admin or repo-admin identity that can accept the GitHub App installation. Document the per-adopter install ceremony in ADOPT-001 §12.7.1 or a new §12.7.16, including the exact GitHub UI path (Settings → Integrations → GitHub Apps → Install) and any org-level approval workflow that may gate the install.

- **TF-PIM-001-SEC-005 — 2026-07-21 quarterly review extension.** The D-031 quarterly bus-factor-1 review agenda (currently: second-maintainer escalation, CODEOWNERS coverage) must be extended to include: (a) App-key rotation verification (confirm key was rotated within the SOP interval); (b) App installation audit (confirm no unexpected installations beyond the 5-cohort adopters); (c) App scope audit (confirm `repository_permissions` remains `{ contents: read }` on `jrnb2024/standards-control-plane` only, with no scope creep). Evidence format: `gh api /app/installations --jq '.[].account.login'` output committed to `docs/reviews/WP-SCP-020/branch-protection-log.md` as a new section.

### Convergence signal

**Strong C**

The sec lens has no reservations about Path C that would push toward Path A or Path D. Path A's permanent exposure is the dominant disqualifier from a threat-model standpoint; Path D's attestation-parity gap and new-pipeline risk surface are secondary disqualifiers. Path C's risks (App-key custody, install ceremony, third-party action dependency) are all tractable with standard SCP operational discipline and are structurally recoverable. The risks generated are enumerated in TF-PIM-001-SEC-001 through TF-PIM-001-SEC-005 and are appropriate for the impl WP plan-doc to inherit.
