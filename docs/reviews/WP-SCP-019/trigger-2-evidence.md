## Caveats (ack, not block)

**Caveat 1 — SHA verification method.** SCP's §Q4.10 Evidence line
anticipated "`shasum -a 256` receipts." CT's filing substitutes FLA's
`ct-sdk-conformance` CI job (INFRA-034 v1), which enforces the
expected SHA-256 values on every PR against `vendor/ts/` +
`vendor/python/`. Green CI at each merge SHA (#291, `3ff0c92c4`,
`2621d2383`) is the record. SCP accepts: automated continuous SHA
enforcement is stronger in form than a one-time receipt — it closes
both the initial vendoring and future drift. No remediation requested.

**Caveat 2 — Python lockfile interpretation.** FLA convention does
not maintain a separate Python lockfile (no `poetry.lock`, `uv.lock`,
or `pip-compile`-generated artefact). `backend/requirements.txt` is
the canonical pin AND the lockfile-equivalent for FLA's Python
project setup. CT flagged this explicitly in the filing. SCP
accepts: the pin line `ct-auth[fastapi]==0.8.1` carries the same
authority as a lockfile entry for a project that maintained one.
§Q4.10 conditions 2 and 3 are effectively merged for Python under
FLA's convention. No remediation requested.
