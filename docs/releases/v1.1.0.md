## What ships — SCP-R-004 (waiver `reason` must cite an issue/PR/decision URL)

**Threshold: warn** (per VERSIONING.md baseline for new rules; promotion to `deny` default would be a separate RFC for v2.0.0+).

The rule fires on each waiver entry in a waivers payload (top-level JSON array per `schemas/waivers-file.schema.json`) whose `reason` field is a non-empty string but does NOT contain at least one HTTP(S) URL. The rule's promise is "a URL exists in the reason"; richer content checks (URL points at a real issue, URL resolves successfully, etc.) are explicitly out of scope at v1.1.0 — see RULE-001 §4 FP-3 + §5 case 5 for the residual-bypass framing.

Adopters bumping their SCP federation primitive pin from v1.0.x to v1.1.0 will see `::warning::` annotations on PRs that touch a waivers payload containing entries with non-URL `reason` text. The warning is **non-blocking** — it does NOT fail the gate or block merge. Adopter-side response options are documented in `docs/adoption/ADOPT-001-project-onboarding.md` §12.7.14 (NEW in this release):

1. **Gradual amendment** — add a URL to each waiver's `reason` on its next-touch PR. Lowest-friction.
2. **`.scp/rule-config.yaml disable: true`** for SCP-R-004 with `expires_at: <90-day window>` and `justification: "transition window — amending legacy waivers to include URLs"`. Use this if you need a transition window.
3. **Bulk-amend cleanup PR** — amend all waivers in one PR. Highest-friction but most complete.

The rule was authored via the federation primitive's first dogfood of the rule-RFC process (slice 020L, 2026-05-02). RULE-001 (`docs/reviews/rule-proposals/RULE-001-waiver-reason-must-cite-issue-or-pr.md`) is the canonical specification.

## What changes for adopters

### New annotation surface

- **`::warning file=output/findings/waivers.json,title=SCP-R-004::<message>`** — fires on each non-URL waiver entry. Message format per RULE-001 §3.3: `SCP-R-004 waiver entry N (rule_id=<rid>, finding_id=<fid>): reason field must contain a decision-artifact URL (issue, PR, or decision log entry). Found reason text: "<truncated-reason>"`. Truncation is 80 chars + trailing `…` if the original exceeds the budget.
- **No new `SCP-EXXX` infrastructure code.** The closed `SCP-EXXX` codespace per ADOPT-001 §12.7.7 remains unchanged. SCP-R-004 carries its own rule ID in the annotation `title=` (matching the existing per-rule annotation pattern when `annotate=true`).

### No breaking changes

- `workflow_call.inputs` on `policy-check.yml` — unchanged.
- `schemas/policy-check-summary.schema.json` + `schemas/rule-config.schema.json` + `schemas/waiver.schema.json` + `schemas/waivers-file.schema.json` — unchanged.
- SCP-R-001 / SCP-R-002 / SCP-R-003 — unchanged.
- Adopters with no waivers OR whose waivers all already include URLs in `reason` see **no behavioural change**.

### Workflow rendering — the warn-baseline branch

`.github/workflows/policy-check.yml`'s "Render deny annotations and enforce threshold" step now distinguishes warn-baseline rules from deny-baseline rules. Warn-baseline rules fire `::warning::` instead of `::error::` AND are excluded from the threshold check so they cannot block merge. The allow-list at v1.1.0 is `WARN_BASELINE_RULES = {"SCP-R-004"}` — hardcoded inline; if a 2nd warn-baseline rule lands the team will consider promoting this to a data-driven `policies/rule-baselines.yaml` manifest (TF-020P-001 forward-compat candidate).

A future promotion of SCP-R-004 from warn → deny default (earliest plausible v2.0.0) would (a) require its own RFC-NNN proposal per `docs/reviews/rule-proposals/README.md` §When to file, AND (b) remove SCP-R-004 from the `WARN_BASELINE_RULES` set so the existing deny-baseline rendering applies.

## How adopters can verify

After bumping the SCP federation primitive SHA pin to the v1.1.0 commit, the next adopter PR run on a repo with at least one waiver entry whose `reason` lacks a URL should show:

- `policy-check / scp/policy-check`: **PASS** (warn-baseline does not block).
- A `::warning::` annotation in the PR Files-Changed tab on `output/findings/waivers.json` titled `SCP-R-004` with the message format specified in §3.3.
- `scp/policy-check-readback` summary unchanged (the readback step's enabled-rules count grows from 3 → 4 to reflect the new rule, consistent with existing readback shape).

If `policy-check / scp/policy-check` FAILS (red X) on a PR whose only finding is SCP-R-004, that is a regression — please file an issue at `https://github.com/jrnb2024/standards-control-plane/issues/new` referencing the PR number, the workflow run ID, and the policy-findings.json content.
