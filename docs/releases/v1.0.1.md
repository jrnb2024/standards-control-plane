# v1.0.1

**Release date:** 2026-05-02
**Slice:** WP-SCP-022 020M — supply-chain hash-pinning for Python deps
**Bump type:** PATCH (per `policies/VERSIONING.md` — internal hardening; no behaviour change for adopters)
**Closes:** TF-020H3rg-002 (filed at 020H.3 R1 safety MIN-SAFE-006)

## What ships

A single supply-chain hardening: the SCP federation primitive's two YAML/JSON-validating workflows now install Python dependencies with **`pip install --require-hashes -r requirements/policy-check.txt`** instead of inline `pip install pyyaml==6.0.2 jsonschema==4.23.0`. The lockfile is generated by `pip-compile --generate-hashes` from `requirements/policy-check.in` and pins the full transitive closure (`attrs`, `jsonschema-specifications`, `referencing`, `rpds-py`) with all-platform wheel SHA256 hashes.

A PyPI compromise of any pinned version would cause `pip install --require-hashes` to refuse the install. Without this change, a hash-mismatched wheel would silently substitute on the next workflow run.

## What changes for adopters

**Nothing.** Top-level pins (`pyyaml==6.0.2` + `jsonschema==4.23.0`) are unchanged from v1.0.0. The reusable workflow's `workflow_call.inputs` are unchanged. The `policy-check-summary.schema.json` and `rule-config.schema.json` shapes are unchanged. All three SCP-R-NNN rules are unchanged.

Adopters who pin SCP by SHA via Renovate (`renovate/v1.0.0` preset) get this on their next preset-bump PR. Adopters who manually SHA-pin can bump at their own cadence; the older v1.0.0 SHA continues to work.

## How adopters can verify

After bumping the SHA pin to the v1.0.1 commit, the next adopter PR run should show:

- `policy-check / scp/policy-check`: PASS.
- The "Ensure caller-data dependencies" step run-log (visible in the Actions UI) reads `pip install --user --require-hashes -r .scp-runtime/requirements/policy-check.txt`. The same applies to "Enforce break-glass pairing gates" if `scp_bypass: true`, and to "Validate policy-check summary schema".
- Each install step is followed by a version-pin assertion (`python3 -c 'import yaml, jsonschema; assert yaml.__version__ == "6.0.2"; assert jsonschema.__version__ == "4.23.0"'`). The assertion fails closed with a SCP-E001 / SCP-E004 annotation listing the actual versions detected, defending against any future-PR drift that might re-introduce a presence-only conditional skip without updating the lockfile pins.

**Behavioural change vs v1.0.0.** v1.0.0's install pattern was `if ! python3 -c 'import yaml'; then pip install --user pyyaml==6.0.2; fi` — a presence-only conditional which would skip the install on any runner that had `pyyaml` importable at any version (notably ubuntu-24.04 hosted runners ship `pyyaml 6.0.1` from apt, satisfying the import). The version-pin was therefore not actually enforced on hosted runners pre-v1.0.1. v1.0.1 fixes this by always running `pip install --require-hashes`: pip is idempotent if the exact pinned version is already in user-site, otherwise it downloads the wheel, hash-verifies against the lockfile, and installs to user-site (which takes precedence over system-site per PEP 370). The post-install assertion confirms the correct version is now active. Adopters who watch the step run-log will see the install path executing on every PR, including the hash-verification line for the wheel actually downloaded.
